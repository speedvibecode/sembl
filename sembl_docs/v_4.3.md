## 2. Formal Definitions

### 2.1 Entity
Structured reusable data object.

Requirements:
- ≥1 field
- Explicit types
- Reusable across interfaces
- No UI/temporary state

---

### 2.2 Interface
Executable contract.

MUST include:
- input schema
- output schema
- success example
- ≥1 failure example
- preconditions
- postconditions
- referenced entities

---

### 2.3 Feature
User capability mapped to ≥1 Interface.

---

### 2.4 Integration Contract
Defines composition across interfaces.

MUST include:
- ordered sequence of Interfaces
- data flow mapping
- error propagation rules

**Example Structure:**
```text
Flow: CreateExpenseFlow
Steps:
1. addExpense → output.expense.id → input.expense_id of next
2. updateSummary
Errors:
- if addExpense fails → abort
- if updateSummary fails → rollback (if applicable)
```

---

### 2.5 Design Artifact
UI definition (screens, HTML/CSS, design.md)

MUST be:
- immutable
- source of truth for UI

## 12. Enforcement, Orchestration, and Oversight (FINAL COMPLETION)

### 12.1 Enforcement Strategy (Multi-Pass Validation)

Validation MUST NOT rely on a single agent pass.

Enforcement Procedure:
1. Run Validation Agent Pass A (structural checks)
2. Run Validation Agent Pass B (semantic checks)
3. Run Consistency Cross-Check Pass (compare outputs)
4. Aggregate violations

Rules:
- A violation is valid if detected by ≥1 pass
- Conflicting results MUST trigger re-evaluation
- Max validation passes MUST be bounded

Purpose:
Mitigate LLM hallucination and missed invariants.

---

### 12.2 Integration Contract Formal Schema

Integration Contracts MUST explicitly define data flow and control flow.

Required Structure:

```text
Flow: <name>

Steps:
1. Interface: A
   Output: { field_a }

2. Interface: B
   Input Mapping:
     field_b ← A.field_a

Error Handling:
- On A failure → abort
- On B failure → compensation action OR retry

Transaction:
- atomic: true/false
- rollback strategy: <defined or none>
```

Rules:
- All data mappings MUST be explicit
- No implicit field transfer allowed
- Error propagation MUST be defined

---

### 12.3 Task Graph Orchestration

Task Graph MUST be executable as a dependency graph.

Each Task MUST define:
- dependencies
- execution order
- input/output bindings

Execution Model:
- DAG (Directed Acyclic Graph)
- Topological execution required

Rules:
- No circular dependencies allowed
- Integration tasks MUST appear as orchestrated nodes

---

### 12.4 Cross-Cutting Concern Handling

Cross-cutting concerns MUST be modeled as shared Interfaces or middleware layers.

Allowed Patterns:
- Shared Interface (e.g., validateRequest)
- Middleware abstraction (applied uniformly)

Constraints:
- MUST NOT duplicate across Features
- MUST remain reusable

---

### 12.5 Human Oversight and Escalation

Human intervention MUST be explicitly defined.

Escalation Conditions:
- Validation fails for ≥ N iterations
- Integration Contract cannot be satisfied
- Conflicting invariant violations persist

Escalation Actions:
- Manual review of Concept Graph
- Manual override of normalization step
- Approval gate before re-execution

---

### 12.6 Tooling Requirements

System requires minimal enforcement tooling:

Required Capabilities:
- Versioned Concept Graph storage
- Graph diffing between iterations
- Deterministic task regeneration
- Validation execution pipeline

Constraint:
Tooling MUST NOT alter system logic, only enforce it.

## 13. Graph Representation (Canonical JSON Format)

All Concept Graphs MUST be represented in structured JSON format.

Markdown or text representations are OPTIONAL and non-canonical.

---

### 13.1 Concept Graph Structure

The Concept Graph MUST conform to the following generic structure:

```json
{
  "entities": [
    {
      "name": "<string>",
      "fields": {
        "<field_name>": "<type>"
      }
    }
  ],
  "interfaces": [
    {
      "name": "<string>",
      "input": {
        "<field_name>": "<type>"
      },
      "output": {
        "<field_name>": "<type | Entity reference>"
      },
      "success_example": {
        "input": {},
        "output": {}
      },
      "failure_examples": [
        {
          "input": {},
          "output": {}
        }
      ],
      "preconditions": ["<string>"],
      "postconditions": ["<string>"]
    }
  ],
  "features": [
    {
      "name": "<string>",
      "interfaces": ["<interface_name>"]
    }
  ],
  "integration_contracts": [
    {
      "name": "<string>",
      "steps": [
        {
          "interface": "<interface_name>",
          "input_mapping": {
            "<target_field>": "<source_reference>"
          }
        }
      ],
      "error_handling": ["<rule>"],
      "transaction": {
        "atomic": "<boolean>",
        "rollback": "<strategy | null>"
      }
    }
  ]
}
```

---

### 13.2 Structural Requirements

* All keys MUST be present (empty arrays allowed)
* Entity references MUST match defined entities
* Field types MUST follow allowed type system
* Interface examples MUST be structurally valid
* Integration mappings MUST reference existing fields

---

### 13.3 Type System

Allowed types:

* string
* number
* boolean
* array<type>
* object (only via Entity reference)

---

### 13.4 Enforcement Rules

* JSON is the ONLY canonical representation
* All transformations MUST operate on JSON
* Validation MUST operate on JSON
* Task generation MUST consume JSON

---

### 13.5 Non-Canonical Formats

Markdown or text representations:

* MAY be generated for readability
* MUST NOT be used for execution
* MUST be derived from JSON

---

### 13.6 Example Usage (Optional)

Implementations MAY include concrete examples for clarity, but:

* MUST NOT infer structure from examples
* MUST validate against schema

This ensures:
